# Repository code style

These conventions apply when authoring or changing Hyperfocus repository code. They
do not govern projects operated or generated by the Harness. Apply them to new and
modified code; migrate existing code deliberately rather than hiding architectural
problems with mechanical rewrites.

Repository-owned executable scripts should be authored as TypeScript and run through
Bun, including helpers shipped with root repository skills. Keep packaged Harness
and user-project automation self-contained; this repository convention is not a
requirement for people operating projects through the Harness.

Prefer concise variable names when they remain unambiguous in their local scope.
Length is not clarity: keep domain terms that distinguish similar values, but avoid
repeating context already supplied by the function, module, or type.

## Imports and module boundaries

- Across a package or application ownership boundary, import through a real,
  manifest-backed `@hyperfocus/...` export. Do not use a relative path that escapes
  the owning package or application.
- Within one package or application, import the owning implementation module
  directly with a relative path. Do not route internal dependencies through a
  re-export-only barrel or through the package's own public facade.
- Use `index.ts` as a public barrel only at the root of a published package or
  published subpath. Keep internal logic on direct file imports even when a nearby
  public barrel exports the same symbol.
- Prefer explicit named re-exports over `export *` so the public surface cannot grow
  accidentally. Mark barrel-exported JavaScript as side-effect free in the owning
  package manifest; list real CSS or initialization side effects explicitly instead
  of disabling their retention.
- Package-consumer and public-contract tests may import public barrels. Unit and
  implementation tests import the module under test directly so an unrelated barrel
  export does not flatten their dependency and invalidation graph.
- If no public export can represent a cross-boundary import, resolve the ownership or
  public-API gap. A TypeScript-only alias must not disguise a private dependency or
  an architecture inversion.
- Repository lint should autofix a cross-boundary relative import only when resolution
  identifies one unambiguous exported `@hyperfocus/...` path. Ambiguous, private, or
  inverted dependencies should be reported without a speculative fix.

## Type modeling

- Make the implementation the source of truth. Prefer inference for values and return
  types; avoid a separate local interface, annotation, or `satisfies` expression that
  merely repeats an object or factory shape.
- Derive exported types from the canonical runtime source: `z.infer` for schemas,
  `typeof` for literal objects and registries, and `ReturnType<typeof createFoo>` for
  factory-owned APIs. Derive input types from an implementation signature when a
  caller needs to name them.
- Use an explicit type only where TypeScript cannot infer one from the implementation,
  such as an empty mutable collection, recursive definition, external boundary, or
  function input. Keep that contract beside its implementation rather than in a
  parallel interface file for a local-first structure.

## Assertions and narrowing

- Prefer validation, control-flow narrowing, and type guards over type assertions.
  Repeated assertions indicate that the boundary or state model should be improved.
- `as const` is literal inference, not an unsafe escape hatch, and is allowed.
- Do not use `as SomeType` to claim a shape the compiler has not proved. Use another
  `as` only at a genuinely foreign or unknown boundary, after a runtime invariant the
  compiler cannot express, or for an unavoidable platform or library typing gap. Add
  a nearby rationale when that invariant is not self-evident. Avoid double assertions;
  a repeated need for them is type-model debt.
- Bounds-proven non-null access in measured hot loops may document one surrounding
  capacity or index invariant instead of adding a helper or per-expression comment.

## Composition and classes

- Use functions, closures, plain objects, and small factories. A resource-owning
  factory returns explicit lifecycle operations such as `dispose`; lifecycle and
  state isolation are not reasons to introduce a class.
- Do not introduce repository-authored classes or application inheritance hierarchies.
  When an external platform literally requires subclass syntax, keep that adapter at
  the boundary and document the requirement.
- Migrate an existing public constructor through an explicit compatibility plan and
  consumer verification. Compatibility affects sequencing, not the factory-first
  destination.

## Component styles

- In a TSX module with local StyleX, place top-level `stylex.create` declarations after
  imports, types, and constants they depend on, but before the first exported render
  component. All local StyleX declarations precede the first component when a module
  exports several.
- A nearby `*.styles.ts` module is allowed when styles are shared or when extraction
  keeps the component readable and within source-structure limits. Import it before
  component declarations.
- Use StyleX for static component presentation. Inline styles are for runtime-computed
  geometry, sizes, or custom properties. Global reset, theme, fixed-canvas, and vendor
  boundaries follow [the StyleX integration policy](stylex.md).

## Enforcement

Keep no more than 25 authored source files directly in one directory. When a domain
approaches that limit, group files by cohesive responsibility and keep internal
imports pointed at the owning implementation module rather than adding convenience
barrels. Existing crowded directories are ratcheted downward by the source-structure
baseline and may not grow.

Prefer a ratcheted check over a repository-wide rewrite. Autofix only transformations
whose target and behavior are unambiguous; leave architectural decisions as explicit
findings. Repository checks and their regression tests live under `scripts/` and run
through `bun check`. Run `bun run check:code-style` for this policy alone. When a
change removes existing debt, run `bun run ratchet:code-style`; the command can lower
or delete an existing count in `scripts/code-style-baseline.json`, but cannot approve
new debt or growth.

## Agent context hygiene

Before repository context is sent to another model or subagent:

- exclude generated output, lockfiles, and fixtures unless the task directly targets
  one of them and a small excerpt is necessary;
- remove trailing whitespace from every included line; and
- collapse consecutive newline characters to one newline in machine-composed context.

Apply this normalization to delegated context and handoff messages, not to repository
files or user-authored content. Prefer file paths and focused excerpts over copying
whole files.
