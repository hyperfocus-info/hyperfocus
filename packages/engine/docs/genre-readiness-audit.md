# Genre remix readiness audit

This audit uses 25 plausible remix games to test whether Hyperfocus is usable beyond a collection of isolated APIs. Each idea is assessed at three levels:

- **Beginner:** can start from a documented two-file template, edit obvious values, play, save, and build without writing engine glue.
- **Intermediate:** can extend behavior in ordinary typed source, use live reload and diagnostics, and leave the editor without translating proprietary data.
- **Professional:** can profile, automate, operate, migrate, and ship representative content at a controlled memory, frame, storage, and network budget.

The canonical project remains exactly `.hyperfocus/project.json` plus `.hyperfocus/assets.hfp`. Authored TypeScript, shaders, tests, and server code are ordinary optional source outside that directory. Builds, neutral exports, caches, saves, and deployment state are disposable outputs, not additional canonical project files.

## Cross-genre friction by experience level

### Beginner

The strongest path is data-driven 2D, with a complete bounded 3D starter alongside it. Six starters (`top-down`, `grid`, `platformer`, `narrative-rpg`, `authoritative-room`, and `3d-action`) create only the canonical pair. The beginner verification edits a value without changing file count, watches last-good live reload survive a broken edit, rebuilds, drives the runtime, and removes its temporary workspace. Standalone builds integrate input, collision, platformer or rigid 3D motion, navigation, audio, narrative, and browser save profiles.

Remaining beginner friction is concentrated in specialized authoring: touch/rebinding UI, card/hotspot editors, large content batch operations, and genre-specific 3D controls or inspectors. These should be templates or inspectors over the same portable data, not generated source forests.

### Intermediate

The intermediate path is deliberately editor-optional. `build:game` bundles transitive ordinary TypeScript in memory into one offline HTML file; `dev:game` watches only the canonical pair and reachable authored modules, keeps the last good build on errors, and emits bounded live-reload events. Neutral export recovers canonical JSON and named ordinary assets with SHA-256 diagnostics. Public subpaths keep DOM, browser, server, renderer, and optional legacy Three.js boundaries explicit.

The main parity gap is arbitrary TypeScript execution inside browser Editor Play. Source-aware CLI Play/Build is complete, but the editor cannot safely discover and compile arbitrary local modules without an explicit directory/source permission and compiler strategy.

### Professional

The professional foundations now include deterministic package builds, runtime/declaration parity, external-consumer smoke tests, bundle byte budgets, fixed-capacity hot paths, browser-system acceptance, crash-safe project pair swaps, portable backups, signed one-use server admission, bounded metrics, graceful drain, and provider-neutral persistence interfaces. First-party WebGL2 and physics paths reduce dependence on Three.js or an external solver, while glTF/JSON/ZIP/SHA-256/IndexedDB remain standards-based escape boundaries.

The remaining professional friction is breadth beyond the verified reference paths: exact oriented/angular collision and general joints, fuller texture/environment PBR and HLOD, complex content merge/lint workflows, managed deployment provisioning/consensus, and long-duration project-specific soak/restore drills. These are disclosed extension boundaries, not hidden hosted dependencies or proprietary project-format requirements.

## Scoring rule

A category reaches 8/10 only when a clean project exercises its authoring, runtime, persistence where applicable, build, diagnostics, and browser or server acceptance path. A unit-tested helper alone is capped below 8. The current numeric assessment and exact commands live in [readiness-roadmap.md](./readiness-roadmap.md); this document supplies the genre-by-genre pressure test behind those scores.
